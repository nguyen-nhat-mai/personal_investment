What this is

A data-engineering project with two goals at once: practice real orchestration/ modeling/testing patterns, and actually answer where in France spare cash is worth putting — property, a PEA equities watchlist, or a gold/crypto watchlist. Five Airflow DAGs land raw data in BigQuery; dbt models it through a layered warehouse with automated tests; a small Python script exports the results as static JSON; and this page is a dependency-free HTML/CSS/JS dashboard reading that JSON, hosted for free on GitHub Pages. Stack: Airflow · BigQuery · dbt · Python · vanilla HTML/CSS/JS. The sections below focus on the architecture and the reasoning behind it — the full source, with every model and DAG, is in the repo linked in the footer.

Ingestion — Airflow

Five DAGs, one per source (dvf_ingest, insee_ingest, tax_ingest — each roughly yearly or twice-yearly — equities_ingest and alternatives_ingest, daily via yfinance). Each downloads, lightly cleans, and appends to its own raw_* BigQuery table.

Orchestration — dependency-driven, not cron

A sixth DAG, dbt_transform, has no schedule of its own. Every ingest task declares an Airflow Dataset outlet on its raw table; Airflow triggers dbt_transform only once every raw table has updated at least once since its last run — Dataset-list scheduling is AND, not OR. That's a deliberate choice: a fixed cron (e.g. "run dbt nightly at 2am") would sometimes fire against a half-refreshed warehouse if one source's ingest ran late or failed; this can't, by construction.

Warehouse & transforms — BigQuery + dbt

dbt builds three layers on top of the raw tables: staging (1:1 cleanup per source), intermediate (aggregations, joins, CAGR math), and marts (the four business-facing tables everything else reads). dbt tests (uniqueness, non-null keys) run at each layer.

Export — manual, reviewed

scripts/export_marts.py reads the marts and writes docs/data/*.json. Run by hand, not from CI — see "Design decisions" below for why.

Presentation — static HTML/CSS/JS

No build step, no npm install, no CDN scripts — the browser reads <link>/<script src> tags directly, served for free by GitHub Pages.

Design decisions

The interesting parts of a data project are rarely the happy path — they're the trade-offs made along the way. These are the ones worth explaining out loud.

Staging → intermediate → marts, not one big query

Staging exists specifically to absorb source quirks so nothing downstream has to know about them — e.g. the two INSEE-sourced data.gouv.fr commune files use inconsistent ;/, delimiters and non-standard column names (disp_mediane, not the more common INSEE medXX convention); both are handled once, in staging, and verified against the real files. Intermediate holds aggregation math (population CAGR, price CAGR) that multiple marts would otherwise have to duplicate. Marts are the only layer the dashboard and export script are ever allowed to read — a boundary that keeps "what the UI shows" and "how it was computed" decoupled.

Data-quality guardrails live in SQL, not in the dashboard

Implausible DVF prices (below €100/m² or above €30,000/m², a bound found from a real anomaly in the data) and non-market transactions (forced auctions, exchanges, expropriations) are filtered in the intermediate layer, before a commune ever gets a score. A commune also needs a minimum population and sale count to be scored at all. Catching this in SQL, once, means every consumer — the dashboard, a future BI tool, an ad-hoc query — inherits the same clean baseline instead of re-implementing the filter.

Derive facts instead of hand-typing them

A ticker's country is derived from its ISIN prefix (legal domicile), not typed by hand into the watchlist seed. That single change caught 5 real mistakes in the original list: ArcelorMittal and Eurofins are Luxembourg-domiciled, Airbus/Stellantis/STMicroelectronics are Netherlands-domiciled — despite all five reading as "French" CAC 40 names. Legal domicile is what actually governs PEA eligibility; hand-typed labels had silently encoded the wrong fact.

Liquidity is modeled as convertibility, not trading volume

The alternatives watchlist's liquidity label (illiquid/medium/liquid) describes how easily you could turn a holding into cash if you actually held it that way — not how liquid its price ticker is. Physical gold is labeled illiquid even though its price proxy, GC=F, is one of the most liquid futures contracts that exists; conflating the two would have been an easy, wrong shortcut. The label isn't just descriptive — it gates which rows the wealth simulator is allowed to average into its "liquid instruments" growth assumption.

Null instead of a fabricated number

Return, volatility, drawdown, Sharpe, and vs.-benchmark are all left null until a ticker has 60+ trading days of ingested history. Short-history extrapolation fails in both directions — an absurd annualized return from a noisy few-day average, or a falsely-flattering near-zero drawdown from a ticker that just hasn't lived through a bad week yet. Showing "–" is a correctness choice, not a missing feature.

Manual, reviewed publish step — not CI auto-deploy

The export script is run by hand, its diff reviewed, then committed — it doesn't run in CI. Two reasons: no GCP credentials need to live in a CI environment, and everything under docs/ becomes public the moment GitHub Pages serves it, so publishing stays a deliberate, reviewed act rather than a side effect of a green pipeline.

Zero-build static frontend

Plain HTML/CSS/JS, split by concern (utils.js/charts.js are shared primitives; one file per tab; main.js bootstraps and wires load order). No framework, no npm dependency tree, no CDN scripts to trust. It's auditable by view-source, has no dependency-supply-chain surface, and costs nothing to host.

Wealth simulator runs entirely client-side

Slider inputs never leave the browser; the only network call fetches already-public aggregate assumption JSON. Its allocation logic is a waterfall, not a blended-rate shortcut: every euro fills Livret A then LDDS first, then splits between a preservation tier and a growth tier by risk tolerance, with PEA overflow past its real €150,000 contribution cap falling back into the preservation tier — modeling the order a real French investor actually fills their accounts in. Modeled growth rates pull a live BigQuery-sourced figure but clamp it to ±20%/year and fall back to a fixed illustrative rate below a history threshold: even a diversified benchmark ETF's 2-year figure (17.9%/year) was too high to compound realistically over a 20–40 year horizon.

Two real bugs this pipeline caught

Worth calling out on purpose: both were found by the pipeline's own guardrails, not by manually eyeballing output, and both are fixed at the source with a defensive backstop downstream.

One ticker, two formula bugs — GLE.PA

Société Générale's ticker exposed two independent issues. First, period return computed as a single point-to-point comparison briefly showed +327% off one glitchy price; fixed by taking the median of the first/last 5 trading days' price instead, so one bad data point can't swing the figure alone. Second, annualizing via power(1 + avg_daily_return, 252) - 1 (raising the arithmetic mean of daily returns to the 252nd power) briefly showed 121%/year against a true geometrically-annualized figure around 25–30%/year for the same prices — arithmetic mean is always ≥ geometric mean, more so for volatile stocks. Fixed with proper geometric annualization: power(last/first, 252/trading_days) - 1.

Placeholder rows counted as trading days — GLD

Batching weekday-only tickers (GC=F, GLD) alongside 7-day/week crypto (BTC-USD, ETH-USD) in one yf.download call unions every ticker's date index, leaving an all-NaN placeholder row for the weekday tickers on every weekend/holiday only crypto trades. Those placeholder rows were counted as trading days, deflating the 252/trading_days annualization exponent — confirmed concretely: GLD reported 12.7%/year against a true ~18.9%/year for the same prices. Fixed at the source (the ingest DAG drops all-NaN rows before upload) and defensively in the staging model (filters adj_close is not null), so already-ingested raw data self-heals on the next dbt run without a re-ingest.

Where the data comes from

French real estate — DVF

"Demandes de Valeurs Foncières" — essentially every property sale in France, published as open data by the French government (data.gouv.fr). Refreshed roughly twice a year. Doesn't cover Alsace-Moselle (57/67/68), which uses a different land registry, or most overseas départements.

Commune demographics & income — INSEE

Population, area, density, and median household disposable income per commune, from two INSEE-sourced data.gouv.fr datasets. Reference data, refreshed roughly yearly.

Equities & alternatives — Yahoo Finance

Daily adjusted prices via yfinance on weekday evenings: the PEA watchlist (CAC 40 + a handful of non-French EU blue chips also PEA-eligible under the EU/EEA-headquarters rule, e.g. ASML, SAP + PEA-eligible ETFs), and a separate gold/crypto watchlist (GC=F, GLD, BTC-USD, ETH-USD). Legal PEA eligibility and a specific broker's actual custody support aren't always the same thing — verify with your broker.

Property tax rates — DGFiP

Commune-level building property tax rates, from the French tax authority's "Fiscalité locale des particuliers" dataset. Reference data, refreshed yearly. Shown in the Real estate table; contributes a guard-rail penalty above egregious outliers, not yet a full weighted score factor.

Population history — "Populations légales" 2017-2021

Year-by-year official population per commune, feeding the score's population-growth factor. A community republish (data.gouv.fr org "icem7") of INSEE figures rather than first-party INSEE hosting — the official INSEE bulk API proved too slow/unreliable to fetch reliably from this environment, so this source is hosted on the same fast infrastructure DVF uses.

Full per-metric methodology (exact weights, formulas, and every simplification) lives in each tab's own "How is this calculated?" panel, kept next to the numbers it explains rather than duplicated here.

Known limitations & what's next

This is a research aid built for learning, not investment advice. Score weights are hand-picked and meant to be tuned, not authoritative; both watchlists are snapshots that drift over time (the alternatives one is also deliberately narrow — one gold proxy, one gold ETF, two cryptocurrencies — rather than a broad basket); and even after the data-quality filters, communes with only a handful of sales can show noisier numbers than well-traded ones — transaction counts are shown everywhere precisely so that's judgeable, not hidden. DPE (energy rating) isn't ingested yet — it would need a new ADEME source and its own Airflow/dbt pipeline. Ideas not yet built: a BI layer (Metabase/ Looker Studio) on top of the marts for ad-hoc exploration, and a "where should my cash go" mart comparing real, inflation-adjusted yield across Livret A, mortgage rates, and the equities watchlist.
